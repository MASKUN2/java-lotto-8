**예외시 재입력을 처리하는 계층은 어느 계층일까? 어떻게 구현할까?**  
이전 과제에서는 잘못된 입력에 의한 예외복구를 수행한 적은 있었다. 만약 문자열이 빈 문자열로 입력되었다면 이를 숫자 0으로 처리하여 계속 애플리케이션을 실행할 수 있었다.  
이 경우에서는 try catch 구문에서 메서드의 반환 값을 변경하면 되어서 처리 메서드 밖에서는 제어흐름이 변경되지 않았다.  
이번 로또 미션에서는 입력을 다시 받아야하는 흐름제어가 필요했다. 즉 여러 메서드가 연결되어 있는 단위 동작을 검증하고 실패시 다시 시도해야했으므로 이를 처리해야하는 계층으로 어디가 적합한지 고민되었다.

나는 헥사고날 아키텍쳐를 지난 주차에 이어서 적용했는데 재입력 흐름제어를 헥사곤 안에서 수행하는 것은 좋지 않은 판단이라고 생각했다. 왜냐하면 재입력 흐름제어은 비지니스로직은 아니고, 헥사곤(코어)는 외부 의존성에서
비지니스 로직을 격리한 순수한 도메인 계층이기 때문에 이 계층의 단위 도메인 기능안에서의 흐름제어는 수행할 수 있어도 입력과 연결되어 있는 흐름제어에 직접적으로 헥사곤이 관여해서는 안된다고 생각했다.

다만 헥사곤은 도메인을 가지고 있기 때문에 해당 도메인에서 생기는 불변식을 검증하는 책임은 있다고 생각했다. 따라서 나는 헥사곤에서는 검증을 통해서 도메인 예외를 던지되 재입력 처리를 위한 흐름을 제어하지 않기로
했다. 예외도 곧 메세지이니 이를 수신하는 어댑터에서 이러한 동작을 대신 처리하도록 설계했다.

요구사항에는 예외메세지를 사용자에게 보일때 `[ERROR]` 를 앞에 붙이라고 적혀있다. 나는 도메인에서 예외를 던질 때 메세지에 이를 붙여서 던지는 것은 좋지 않다고 생각했다. 왜냐하면 이 요구사항은 사용자에게
출력하는 표현계층의 영역이라 도메인 계층에서 이를 알아서는 안된다고 생각했기 때문이다. 따라서 나는 어댑터 계층에서 이를 처리하도록 했다.

아이디어는 간단했다. 어댑터에서 try catch 구문안에서 도메인 로직을 요청하고 예외를 잡아서 예외 메시지에 `[ERROR]`을 붙이는 방식이다. 이 방법은 도메인 계층에서 예외를 던질 때 표현계층을 무시해도
되며 어댑터에서 선택적으로 예외를 핸들링 할 수 있다. 나는 재입력 흐름제어가 필요한 일부 기능에 대해서만 도메인 계층으로부터 던져지는 `IllegalArgumentException`을 잡아서 예외 메세지를
출력하도록 했다.

이러한 예외처리는 총 2가지 적용이 기능에 필요했다. 둘 모두 입력을 받는 독립적인 기능이고 같은 예외처리가 필요했기에 이를 단순히 컨트롤러 메서드에서 수행하는 것이 아니라 이를 위해 만들어진 클래스가 예외처리를
제공해주는 편이 좋다고 생각했다. 따라서 아래와 같이 해당 예외처리(재시도 처리)기능을 제공하는 클래스(RetryableExceptionHandlerImpl)와 제네릭 메서드(<T> T handle(
Supplier<T> supplier)를 만들었다.

```java
public class RetryableExceptionHandlerImpl {
    private static final int MAX_TRY_COUNT = 10;
    private static final String ERROR_PREFIX = "[ERROR] ";

    @Override
    public <T> T handle(Supplier<T> supplier) throws ExceededRetryException {
        int tryCount = 0;

        while (++tryCount <= MAX_TRY_COUNT) {
            try {
                return supplier.get();
            } catch (IllegalArgumentException exception) {
                System.out.println(ERROR_PREFIX + exception.getMessage());
            }
        }
        throw new ExceededRetryException(ERROR_PREFIX + "재시도 횟수가 초과하였습니다");
    }
}
```

이 클래스의 handle 메서드는 인자로 Supplier<T>를 받는다. Supplier<T> 는 실행가능한 함수형 메서드이며 실행결과를 T타입으로 반환한다.  
이 함수를 메서드 로컬의 try catch 안에서 예외를 잡고 이를 적절히 처리하여 예외 메세지를 보이고 다시 시도할 수 있다. 재시도 횟수가 초과할 경우 명확한 메세지를 위해 커스텀 예외인
ExceededRetryException가 던지도록 설계했다. 이렇게 핸들링 메서드를 따로 설계하고 구성함으로 테스트가 쉬워지고 Controller가 예외핸들링에 대한 구체적인 내용을 알지 않아도 된다는 점에서
책임이 분산되고 Controller가 절차적 흐름만 제어할 수 있게 되어 무척 코드가 단순해지는 것을 느꼈다.

나는 최종적으로 이 클래스의 인터페이스를 선언해서 컨트롤러의 생성자에서 주입받도록 설계했다. 앱 초기화 로직에서 이 예외핸들러의 인스턴스를 컨트롤러에게 주입해주고 컨트롤러가 필요한 경우 이 메서드를 사용하도록
하게하여 구현을 마무리했다. 이 과정을 통해 다음을 배우게 되었다.

- 예외에 대한 처리 관점에서의 어댑터와 헥사곤의 역할 구분
- 예외 복구처리 구문을 여러 곳에서 재사용하는방법
- 처리 흐름제어에 있어서 중요한 최대 리트라이 카운트, 최종 실패시 던져야할 커스텀 예외

**저수준의 도메인을 집약하는 고수준의 도메인 모델 만들기**  
이번 로또 미션에서 또한 가장 집중한 부분은 도메인 객체의 모델링이었다. 처음 제공된 로또 클래스(Lotto)가 List<integer> numbers 필드를 가지고 있고 이 타입의 필드를 그대로 활용할 수 있었지만
다음과 같은 이유에서 그렇게 하지 않았다.

- Integer 타입은 기본적으로 음수와 0, 그리고 양수라는 지나치게 넓은 범위를 가지기 때문에 로또 클래스가 직접 해당 숫자의 범위를 사전에 검증하는 것은 좋지 않아보였다.  
  로또 번호에 사용되는 숫자는 또한 당첨번호를 뽑거나 보너스 번호를 뽑는 등의 여러 유즈케이스에서 똑같이 활용되어야한다. 어떻게보자면 숫자 범위를 검증하는 로직만 분리하면 될 것 같지만 검증로직은 그 값이 있는
  곳에 함께 있는 것이 훨씬 응집도가 좋다고 생각했다. 따라서 1에서 45라는 숫자를 담을 수있는 Number 불변 클래스를 설계하고 여기서 해당 검증이 이뤄지도록 했다.
- List<>는 자바의 표준 콜렉션 인터페이스다. 그만큼 편한 기능을 제공하지만 6자리 고정이라는 로또번호의 요구사항을 지킬 수는 없다. 이를 우회하기 위해서 로또 클래스에서 숫자가 6자리인지, 또한 중복된 숫자는
  없는지 검증할 수도 있다. 하지만 앞서 Number를 도메인 값 객체로 도출한 것과 비슷하게 6자리의 중복되지 않은 로또번호는 당첨 번호를 뽑는 유즈케이스에서 또한 활용되어야했고 당첨번호는 로또 클래스와는 다른
  유즈케이스를 가지므로 어느한쪽이 포함되어서는 안되었다. 따라서 로또와 당첨번호가 공유할 수 있는 Number의 고정 크기 콜렉션이 필요했었고 이를 위해서 6자리의 중복되지 않은 숫자만을 가질 수 있는
  Numbers라는 불변 일급 콜렉션 클래스를 설계했다. 로또 번호는 해당 콜렉션을 생성자에서 요구하도록 설계했다. 로또클래스는 기존의 number 필드의 타입만 변경되었다.

이렇게 로또 라는 고수준의 도메인 모델을 설계하기 위해서 Number, Numbers라는 좀더 낮은 수준의 도메인 모델을 설계했다. 이러한 저수준 도메인 모델은 해당 수준에 맞는 로직만 가지고 있도록 했다. 예를
들어 number는 거의 순수한 값 클래스이며 Numbers는 앞서 언급한 불변식을 스스로 검증하고 TreeSet을 사용해 스스로 전달받은 번호를 알아서 오름차순으로 정렬하게 하였다. 또한 외부에서는 어떤
Number를 가지고 있는지만 확인하는 boolean has(Number target) 메서드만 노출하였다.

로또는 고수준이고 발급한 로또라는 맥락을 가지고 있기 때문에 이 로또가 당첨번호와 비교하여 어떤 상금을 받을 수 있는지를 판단할 수 있는 당첨 확인 메서드를 추가했다. 해당 메서드의 시그니쳐는
Optional<Prize> evaluate(Drawn drawn)인데 상금 정보를 가지는 Enum 클래스인 Prize와 당첨번호 정보를 가지는 Drawn에 각각 의존하게 되었다. 처음에는 단순히 Drawn을 받고
이에 대한 일치 결과만 반환하는 방식으로 설계했으나 로또 클래스가 고수준이고 로또 클래스가 당첨 여부를 확인하는 직접 비지니스 로직을 가지지 않고 당첨번호(Drawn)의 Math math(Numbers
numbers) 를 호출하여 일치정보가져와서 Prize 의 Optional<Prize> findBy(Match match)를 호출하여 해당하는 상금이 있으면 가져오는 흐름제어만 담당하기 때문에 책임을 분산할 수
있었기에 이를 용인했다.

그렇게 설계된 로또 클래스는 자기 자신의 검증은 모두 하위 클래스에게 위임하고 단순한 흐름제어만을 하더라도 고수준의 API을 노출할 수 있는 가볍고 작은 클래스가 될 수 있었다. 로또 클래스는 검증메서드를 가지지
않아도 되었고 선언된 메서드는 단 2개이며 getter를 제외하고는 당첨번호를 확인을 위한 단순 흐름제어를 하는 고수준의 메서드 하나 밖에 없게 되었다.

앞서 저수준의 도메인 모델들에게 각각의 역할에 맡는 불변식과 메서드를 분산했으므로 이후 다른 기능에서 이 도메인 모델을 사용하는 유즈케이스에서는 불필요한 참조나 메서드 호출 없이 매우 간단히 로직을 구성할 수 있었고
작성한 코드량이 많이 줄어들게 되었다.

또한 이러한 방식은 요구사항 변화에도 강할 것으로 기대되었다. 만약 로또번호가 5개또는 7개로 변경된다면 개발자는 Numbers의 제약조건을 상수 하나를 수정하는 것 만으로 모든 수정이 완료된다. 만약 번호 범위가
1-45가 아니라 1-100으로 수정된다면 Number의 제약조건만 수정하면 모든 변경이 완료된다. 단순히 관련된 기능 하나가 변하는것이 아니라 이를 의존하고 있는 입력, 생성, 처리 기능에서도 직접 비지니스 로직을
구현하지 않고 이 도메인 모델을 사용하기 때문에 코드를 변경할 것이 없어진다. 이것은 내가 도메인 모델 도출에 무척 많이 신경을 쓴 이유이기도 하다.

회고해본다면 이 개발 과정에서 나는 생각보다 확신이 부족했다. 너무 복잡하게 설계하는 것은 아닐까 자기 검열을 지속하기도 했다. 어떻게 보면 지금 필요하지 않은 확장성을 위해서 단순성을 희생하는 결과가 되지 않을까
염려했다. 하지만 결과적으로는 복잡성의 증가는 각 객체의 책임을 분리하고 맡김으로써 최소화하였고 이를 통해 유지보수성과 확장성이라는 두마리 토끼를 얻을 수 있었다. 결과와 별개로 앞서 그러한 우려는 분명 필요한
것이었고 이러한 우려 덕분에 더욱 깔끔한 코드를 만들기 위해서 노력할 수 있었다. 앞으로도 항상 자만하지 않고 또한 너무 소극적이지는 않게 도전을 해봐야겠다는 생각이 들었다. 이 과정에서 어느정도 어떻게 도메인
객체를 모델링 하면 좋을지 그러한 패턴에 대해서 몸으로 익히게 되어 앞으로도 개발에 많은 도움을 줄 것 같다.
